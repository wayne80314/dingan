# 定價模型（修正版：按收件人數計費）

> 本文件是 M0 的定價設計來源，F0 階段不涉及實際收費（F0 只有試點訂金/付費意向驗證，見 `pilot-plan.md`）。

## 1. LINE push 計費的關鍵事實

驗證來源：developers.line.biz 官方文件（2026-08-27 查證，見 `spike/src/types.ts` 檔頭註解）。

> Push message 是**依收件人數計費，不是依 API 呼叫次數，也不是依一次呼叫裡塞了幾個 message object**。一次 Flex Message 送給 5 人的群組 = 5 則訊息額度。送給已封鎖 bot 或不存在的 userId 不計費。

LINE 免費方案／付費方案的訊息額度分級（依 LINE Official Account 官方定價分級,以你實際開通時 LINE 公告的數字為準,此處僅供架構規劃用的量級估算）：

| 方案 | 每月訊息額度（約） |
|---|---|
| 輕用量（免費層） | 200 則 |
| 中用量 | 3,000 則 |
| 高用量 | 6,000 則 |

## 2. 一個活躍群組每月大概花多少額度

假設一個裝修案件在活躍討論期間，一個月產生 **35 次推播**（決策卡確認請求＋提醒＋每日摘要加總的粗估值，實際依案件討論密度浮動），群組平均 **5 人**（業主雙方＋設計師＋工班代表＋機器人不計）：

```
35 次推播 × 5 人/群組 = 175 則/群組/月
```

對照額度分級：

- **輕用量（200 則免費）** ≈ 撐得起 **1 個活躍群組**（175 則已經逼近上限，稍微多推幾次就超）。
- **中用量（3,000 則）** ≈ `3000 / 175 ≈ 17` 個五人群組同時活躍。
- **高用量（6,000 則）** ≈ `6000 / 175 ≈ 34` 個五人群組同時活躍。

**結論**：任何設計公司只要同時有 2 個以上活躍案件在跑，免費層必定不夠用，M0 上線時要在 onboarding 就講清楚「你可能需要付費開通 LINE 官方帳號的訊息方案」，這是 LINE 平台本身的費用，不是「定案」的訂閱費——兩者要在文案上分清楚，避免使用者誤解「付了定案的錢應該就不會被 LINE 收費」。

## 3. 「定案」自己的訂閱方案設計原則

以 **active project**（有進行中討論的案件）計價並限額，而不是單純「群組數」或「訊息則數」——原因見 `architecture.md` §1，group_id 不是租戶邊界，project 才是。

限額維度：
- **Projects**：同時可有幾個 active project
- **儲存空間**：媒體檔案（圖面、照片）的累積儲存量
- **AI tokens**：每日摘要用掉的 LLM token 額度
- **LINE message units**：「定案」自己代發的推播則數上限（獨立於使用者自己開的 LINE 訊息方案額度，這是「定案」系統本身觸發推播的量,例如決策卡確認提醒)

行為設計：
- **只有「有效討論日」才觸發每日摘要推播**——安靜的群組（沒人講話）不推播，不浪費額度也不打擾使用者。
- **「定案 今日」**（使用者主動在群組打 `@定案 今日` 叫出的當日摘要）走**免費 reply message**（LINE 的「回覆訊息」不計入 push 額度，因為是對使用者主動觸發的回應，而非我方主動推播）——鼓勵使用者用指令主動查詢，而不是依賴每日自動推播。
- **接近額度上限時自動降級**，不是直接斷線：改為「只有 `@定案` 指令觸發才回應」，停止自動的每日摘要推播，但決策卡確認等關鍵功能維持運作。
- **到期後進入唯讀期**：能看歷史決策卡與匯出紀錄，不能再新增決策卡或觸發推播，不會立刻刪除資料——避免使用者因為忘記續約而遺失正在進行中案件的稽核紀錄，同時保留續約誘因。

## 4. 這份文件與 F0 的關係

F0 階段的 `spike/` 完全不涉及計費邏輯（沒有 outbox、沒有 entitlements 表），但 `spike/src/panel.ts` 有一個粗略的月用量統計（`queryPushUsageThisMonth`），是用來讓 Wayne 在**跑 Spike 測試時**知道自己有沒有快把 LINE 免費額度用光，避免測到一半被 LINE 擋掉——這是開發輔助用途，不是本文件所述的正式計費系統。
